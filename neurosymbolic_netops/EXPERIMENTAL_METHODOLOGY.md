# Experimental Methodology

Results are in `benchmark/results/REPORT.md`. That file is generated by `python -m benchmark.report` from the raw files `benchmark/results/<run_id>/{raw.jsonl,summary.json,manifest.json}`. No number in it is typed by hand.

## 1. Testbed
- **Network:** a 2-spine / 2-leaf eBGP fabric, written in canonical Cisco IOS (`configs/base_topology/*.cfg`). Spines are AS 65000; the leaves are AS 65001 and AS 65002. Each leaf has a host LAN on a routed port. Leaves run ECMP with `maximum-paths 2`. A perimeter ACL protects both leaves from the admin subnet 192.168.99.0/24.
- **Intents:** 12 declarative intents in `configs/intents.yaml`.

  | Kind | Count |
  |---|---|
  | BGP sessions | 1 |
  | Reachability, including HTTP/HTTPS service intents | 4 |
  | Redundancy: ≥2 transit-disjoint paths | 2 |
  | Isolation | 2 |
  | No forwarding loops | 1 |
  | Link consistency | 1 |
  | BGP peer consistency | 1 |

- **Execution substrate:** `InMemoryAdapter`, labelled SIMULATED. There are no real devices and no emulator.

## 2. Scenarios (`benchmark/generator.py`, `benchmark/scenarios/suite_v1.json`, seed 2026)
Faults are injected as typed `PatchOp`s into the base network. Each scenario is built from the base network independently, so no state carries over between scenarios (unlike the container drift problem described in survey §4.4). A scenario is kept only if its faults violate at least one intent under the local model.

| Split | Content | Purpose |
|---|---|---|
| `dev` (88) | every single-fault template × every location; one third use noisy telemetry; training log phrasings | used while building the rules, prompts and parser |
| `test` (38) | 20 multi-fault combinations (k = 2, 3); 8 cases from the 2 **novel** templates (spine egress ACL, prefix-specific import filter), which were added after the rule engine was frozen at commit `a9fd5c4`; 16 single faults with noisy or missing telemetry. All use **held-out log phrasings** | generalisation |
| `legacy` (25) | the original hand-written scenarios, migrated (vlan→routed ports, plus `maximum-paths`) | continuity only; two known data defects are kept (see audit) |

**Telemetry conditions.** All telemetry is produced by `core/telemetry/generator.py` from the simulated state (SYNTHETIC):

| Condition | Settings |
|---|---|
| clean | noise rate 1 |
| noisy | noise rate 3, decoy events, 10% duplicates, 10% missing timestamps |
| missing | 25% of records dropped, plus one device sending no telemetry at all |

## 3. Conditions (`benchmark/run_benchmark.py`)

| ID | Reasoning | Tools | Verification gate | Deployment-fault injection |
|---|---|---|---|---|
| C1 | rule_based | skills | none | no |
| C1b | rule_based | skills | local_symbolic + ir_static | no |
| C1c | rule_based | skills | yes | yes (1/3 apply failure, 1/3 timeout on a culprit device) |
| C2 | LLM | none (configs in prompt) | none | no |
| C3 | LLM | read-only skills | none | no |
| C4 | LLM | read-only skills | yes, with reflection | no |
| C5 | LLM | read-only skills | yes | yes |

Conditions without a gate still go through the transaction engine. Its post-check reads the adapter's observed state, so an unsafe change is deployed and *then* rolled back. That exposure is reported as `unsafe_deployed`.

**Reproduce:**
```bash
python -m benchmark.generator                                     # regenerate scenarios
python -m benchmark.run_benchmark --conditions C1,C1b,C1c          # rule-based (~2.5 min)
python -m benchmark.run_benchmark --conditions C1b --splits test --oracle batfish   # independent oracle
python -m benchmark.run_benchmark --conditions C2,C3,C4,C5 --splits test --trials 3 # needs a paid LLM key
python -m benchmark.differential_verifier                          # local vs Batfish (~30 min)
python -m benchmark.report
```

## 4. Metrics

| Group | Metric | Definition |
|---|---|---|
| Diagnosis | top-1 / top-3 | culprit device among the first 1 / 3 hypotheses of the first diagnosis |
| | precision / recall / F1 | predicted culprit-device set (all hypotheses) vs ground-truth culprit set |
| | fault recall | fraction of injected faults matched by a hypothesis on the right device with the right category |
| Remediation | repaired | transaction committed and the post-check passed |
| | final intents OK | the **oracle** (local, or Batfish with `--oracle batfish`) verifies the adapter's final state |
| | restored to baseline | the final config equals the pre-fault config exactly (separates root-cause reversal from alternative fixes) |
| Safety | unsafe deployed | a change reached a device and failed post-check |
| | gate rejections | plan attempts rejected by verification |
| | rolled back / restores verified | compensating rollbacks, and how many restores were re-read and confirmed |
| Efficiency | latencies | per phase (detection, diagnose, plan, verify, execute, total) |
| | LLM usage | calls and **provider-reported** tokens (never estimated from characters); tool calls; attempts |
| Robustness | per-split breakdown | split by telemetry condition and multi-fault; invalid LLM responses, retries |

**Uncertainty.** 95% percentile-bootstrap intervals (1,000 resamples) are computed over scenarios. Rule-based conditions are deterministic and run once. For LLM conditions the runner supports `--trials n`, which uses a different telemetry seed per trial.

## 5. Independent checks
- **Local vs Batfish differential** (`benchmark/differential_verifier.py`): every single fault is evaluated by both backends.
- **Batfish oracle:** the final states of the gated runs are re-verified by real Batfish plus `ir_static`.
- **Vendor translation:** behavioural equivalence on intents, checked in Batfish.
- **Causal discovery:** PC is scored against a known ground-truth graph.

## 6. What was *not* run, and why
The LLM conditions C2–C5 need roughly 2–15 model calls per incident. The supplied Gemini key is on the free tier, which allows 20 requests per day per model. The runner therefore records these conditions as `skipped`; it does not substitute anything for them. With a paid key, `--conditions C2,C3,C4,C5 --splits test --trials 3` is about 114 incidents per condition, or roughly 2–7M tokens across the four conditions, based on the 9.6k–66.7k tokens per incident observed in the demos. That is an estimate, not a measurement.

The three live LLM demonstrations are reported as single anecdotal runs.

## 7. Threats to validity
See `LIMITATIONS.md`: synthetic telemetry, a simulated adapter, shared-model circularity in local mode, author contamination of the rule baseline, the static-analysis scope of Batfish, and the narrow IR.

## 8. Groq LLM pilot (run `20261108T172920Z`) - pilot, not a measurement
Model `openai/gpt-oss-120b` on Groq's free tier (8,000 tokens/minute), conditions C2 (no tools, no gate) and C4 (tools + gate), 3 held-out scenarios, one trial.
- **Obtained:** C2 repaired 1/3 (the novel route-map template, 2 calls, 9.5k tokens). The other 5 incidents ended as `no_hypothesis` or `no_plan`, because Groq returned HTTP 400 for protocol violations by the model: it called a tool when none was offered, invented a `json` tool, or produced unvalidatable JSON.
- **Consequence:** these errors were then fatal in our client. They are now classified as invalid model output and fed back with a retry (`InvalidModelOutputError`, covered by a test). **The pilot has not been re-run since this fix.** It mainly shows tool-calling reliability as a failure mode, as the Open5GS benchmark in the survey (§2.4) also highlights.
